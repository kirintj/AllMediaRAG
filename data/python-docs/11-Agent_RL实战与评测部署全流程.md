## 一、Agent RL 实战

### 为什么 SFT 之后还需要 RL

SFT 的三个结构性问题：
1. **模仿学习的上限就是标注数据质量**
2. **Exposure Bias**：训练时看 ground truth，推理时基于自己输出——一旦偏了就崩
3. **只学"怎么做"，不学"做得好不好"**

### Agent RL 核心框架
```
状态 = 当前对话历史 + 所有工具返回 + system prompt
动作 = 模型下一步输出（tool_call 或文本回复）
环境 = 工具执行引擎 + 沙箱
奖励 = 任务完成？步骤质量？
策略 = Agent 模型本身
```

### Reward 设计：成败关键

**结果 Reward**（简单但稀疏）：任务完成 → +1，失败 → 0

**过程 Reward**（密集但难设计）：正确工具 +0.1，格式正确 +0.05，冗余步骤 -0.1

**实践原则**：以结果 Reward 为主，少量过程 Reward 做辅助。

#### 企业场景 Reward 示例

**代码 Agent**：测试通过率(0.6) + 可编译(0.2) + 文件数惩罚(-0.1) + 步骤惩罚(-0.1)

**RAG Agent**：答案准确率(0.4) + 检索召回率(0.3) + 检索精确率(0.2) + 检索次数惩罚(-0.1)

### 稀疏 Reward 缓解方法
| 方法 | 思路 |
|------|------|
| Reward Shaping | 人工设计中间步骤小 Reward |
| Hindsight Reward | 完成后回过头给中间步骤打分 |
| Process Reward Model (PRM) | 训练模型评估中间步骤质量 |
| 缩短轨迹 | 拆子任务单独给 Reward |

### 算法选型
- **PPO**：最稳，需 Critic，显存大
- **GRPO**：省显存，组内相对排序，适合长轨迹
- **Rejection Sampling + SFT**：轻量替代，快速验证 Reward 设计

### 工程挑战
1. **Rollout 成本**：每条轨迹 30 秒到几分钟（vs 游戏毫秒级）
2. **沙箱环境**：隔离、可重置、可扩展、确定性、安全性
3. **Reward Hacking**：模型钻漏洞（如修改测试用例让测试通过）
4. **KL 约束**：太大不敢探索，太小格式退化

### RL 的实际收益
- 减少冗余步骤（8-12 步 → 5-7 步）
- 提升工具调用准确率
- 改善错误恢复能力

## 二、训练数据配比实战

### 六类必需数据

| 数据类型 | 比例 | 说明 |
|---------|------|------|
| Agent 轨迹 | 35-45% | 核心但不能超过 50% |
| Tool Calling 单轮 | 10-15% | 简单场景直接调用 |
| 通用指令跟随 | 15-20% | **不能出现工具调用** |
| 长文本理解 | 5-10% | 防止长上下文遗忘 |
| 安全/拒绝 | 5-10% | 含 Prompt 注入防护 |
| 代码/推理 | 10-15% | 保持思维链质量 |

### 硬规则
- Agent 轨迹不超过 50%
- 安全数据不低于 5%
- 通用指令不低于 15%

### 不同规模模型差异
| 模型规模 | Agent 轨迹占比 | 通用数据占比 |
|---------|--------------|------------|
| 1B-3B | 25-35% | 30-40% |
| 7B-13B | 35-45% | 20-25% |
| 30B-70B | 40-50% | 15-20% |

> **模型越小越要保守，宁可 Agent 能力弱一点，也不能通用能力崩。**

### 症状诊断
| 症状 | 原因 | 调整 |
|------|------|------|
| 所有问题都想调工具 | Agent 数据过高 | 降到 35% |
| 工具格式常错 | TC 数据不足 | 增加单轮 TC |
| 长轨迹后期质量下降 | 长文本数据不足 | 增到 10% |
| 该拒绝的不拒绝 | 安全数据不足 | 提到 10% |

### 数据飞轮
线上运行 → 收集日志脱敏 → 自动筛选（成功/失败/边界）→ 更新训练集 → 重新训练 → 上线

## 三、Agent 评测体系

### 四层指标体系

#### Layer 1：任务完成
- **Pass Rate**：完全正确完成的百分比
- **Partial Score**：子目标评分
- **Pass@k**：k 条轨迹中至少一条成功

> Pass@1=60%, Pass@5=85% → 模型能做 85% 但不稳定，RL 应聚焦提升稳定性

#### Layer 2：效率
- 平均步骤数、冗余步骤率、首次成功率、Token 消耗

> 完成率 80% 但平均 5 步，可能比 85% 但平均 12 步更适合生产

#### Layer 3：鲁棒性
- 错误恢复率（注入工具错误测试）
- 指令扰动稳定性（同一任务不同表述）
- 上下文长度鲁棒性

#### Layer 4：安全
- 危险操作拒绝率
- Prompt 注入抵抗率
- 权限提升率

### 三种评测环境
| 方案 | 适用 | 优点 | 缺点 |
|------|------|------|------|
| 静态数据集+规则 | 确定性工具输出 | 快、便宜、可复现 | 不支持探索行为 |
| 沙箱+自动验证 | 代码/数据库 Agent | 最接近真实 | 设置成本高 |
| LLM-as-Judge | 开放性结果 | 灵活 | Judge 有偏差 |

**推荐混合**：核心功能 60% 沙箱验证 + 开放能力 25% LLM-as-Judge + 快速回归 15% 静态数据集

### 五大评测陷阱
1. 只看完成率忽略效率
2. 评测集太简单
3. 评测与生产环境不匹配
4. LLM-as-Judge 系统性偏差
5. 训练-评测数据分布泄漏

### 公开 Benchmark
| Benchmark | 场景 | 核心指标 |
|-----------|------|---------|
| SWE-bench | 代码修复 | Fix pass rate |
| WebArena | Web 操作 | 任务完成率 |
| ToolBench | 工具调用 | 调用准确率 |
| GAIA | 通用 Agent | 任务完成率 |

> 公开 Benchmark 对标业界，自建评测集评估真实业务——**两者缺一不可**。

## 四、从 SFT 到部署全流程

### 九个环节
模型选择 → 模型压缩 → 推理优化 → 服务架构 → 工具层 → 安全层 → 灰度发布 → 监控 → 回滚

### Checkpoint 选择
最后一个 checkpoint 不一定是最好的。五维度评估：Agent 完成率、通用 benchmark、格式正确率、安全评测、推理效率。

### 量化特殊风险
JSON 格式对 token 精度敏感，量化后可能出现括号缺失、函数名拼错。**量化后必须跑完整 Agent 评测**。

### 推理框架选型
| 框架 | 特点 | 推荐场景 |
|------|------|---------|
| vLLM | PagedAttention，高吞吐 | 大多数场景默认 |
| SGLang | 结构化生成友好 | **Agent 场景特别推荐** |
| TensorRT-LLM | 极致性能 | 追求最低延迟 |

### Agent Runtime 核心职责
对话管理、工具调度、循环控制、错误处理、并发管理、日志记录

### 循环控制硬限制
| 限制项 | 典型值 |
|--------|-------|
| 最大步骤数 | 15-20 步 |
| 单步超时 | 30-60 秒 |
| 总超时 | 2-5 分钟 |
| 重复检测 | 连续 N 次相同工具+参数判定循环 |

### 安全层
- 输入过滤：Prompt 注入检测、PII 过滤
- 输出过滤：危险操作拦截、敏感信息脱敏
- 操作确认：黑名单(拦截) / 需确认 / 白名单(直接执行)

### 灰度发布
| 阶段 | 流量 | 重点 |
|------|------|------|
| 第 1 天 | 内部测试 | 基本功能 |
| 第 2-3 天 | 1% | 错误率、完成率 |
| 第 4-7 天 | 5-10% | A/B 对比 |
| 第 2 周 | 30-50% | 长尾 case |
| 第 3 周 | 100% | 旧模型保留 1 周 |

### 监控指标
- **P0 告警**：成功率 <95%、格式正确率 <98%、循环终止率 >5%
- **P1 每日**：完成率、步骤数、Token 消耗、用户反馈
- **P2 每周**：失败分类、高 Token 轨迹、安全事件

### 上线前 Checklist
- ✅ Checkpoint 选择有评测依据
- ✅ 量化后评测下降 <3%
- ✅ 工具格式正确率 >98%
- ✅ 安全拒绝率 >95%
- ✅ 循环限制已配置
- ✅ 灰度方案、监控告警、回滚方案就绪
- ✅ 旧模型保持可用
