## 1. 什么是 Agent

### 常见误解
- 更聪明的聊天机器人 ❌
- 能自动调用工具的 LLM ❌
- 会自己规划任务的系统 ❌

### 工程角度的定义
**Agent 是围绕目标持续推进任务的系统**，具备：
1. **接收目标**，而非仅处理单轮输入
2. **保留状态**，而非每次如初次对话
3. **根据中间结果改变后续动作**
4. 需要时**调用外部工具**
5. 在不确定环境中**迭代尝试**

> "Agent 的重点不是'模型更强'，而是'系统闭环更完整'。"

### Agent vs 普通 LLM App

| 普通 LLM App | Agent |
|---|---|
| 用户输入→模型生成→输出 | 目标→多步决策→工具调用→状态更新→继续执行→最终完成 |
| 一次性响应 | 持续执行，形成循环 |

### 判断标准（三件事）
1. 是否围绕**目标持续推进**任务
2. 会不会根据**中间状态改变行为**
3. 是不是**闭环系统**，而非一次性生成

### Agent 最小闭环
```
接收目标 → 读取上下文 → 决定下一步
                ↓ 需要更多信息        ↓ 信息已足够
            调用工具                输出结果
                ↓
          获取返回结果 → 更新状态 → 回到"决定下一步"
```

## 2. Workflow 和 Agent 的区别

### 三类不同系统

| 系统 | 特点 | 典型场景 |
|------|------|---------|
| **普通 LLM App** | 一次输入一次输出 | 问答、摘要、翻译 |
| **Workflow** | 执行路径由开发者预先定义 | 工单分类、简历评分 |
| **Agent** | 系统根据中间状态动态决定下一步 | 开放性探索、多步分析 |

### 核心分界线
> 下一步动作是由开发者**提前写死**，还是由系统根据状态**动态决定**。

### 实用判断方法

**选 Workflow 的信号：**
1. 任务步骤基本固定
2. 执行路径可预先枚举
3. 模型只负责生成不负责决定流程
4. 更在意稳定性和可控性

**选 Agent 的信号：**
1. 需要根据中间结果动态选择工具
2. 需要在信息不足时继续探索
3. 需要围绕目标持续推进
4. 存在开放环境和不确定决策

### 工程实践：组合使用
- **外层**用 Workflow 控制主流程
- **某些节点内部**再放 Agent

> "Workflow 负责确定性流程，Agent 负责不确定环境下的动态推进。"

## 3. Agent 系统的七大核心模块

### 1️⃣ Goal（目标）
定义：任务要解决的问题、输出形式、完成标准。
> 很多 Agent 问题本质上是**目标定义问题**，而非模型问题。

### 2️⃣ State（状态）—— 最易被忽略但最关键
包含：当前任务输入、已完成步骤、已获取信息、中间结果、下一步待办、结束条件

没有明确状态会导致：上下文混乱、重复调用工具、无法恢复执行、难以调试

### 3️⃣ Model（模型）
负责理解任务、决定下一步动作、生成结果。
> **模型只是 Agent 中的一个组件，不是整个 Agent。**

### 4️⃣ Tools（工具）
解决"模型本身做不到"的事：搜索、数据库查询、API请求、文件读写、代码执行

### 5️⃣ Memory（记忆）
- **会话内记忆**：当前任务状态延续
- **跨会话记忆**：长期偏好、历史记录

### 6️⃣ Planner / Policy（决策逻辑）
核心问题：下一步是否需要工具？用哪个？什么时候停止？

### 7️⃣ Evaluator / Guardrails（评估与约束）
检查输出格式、验证证据充足性、控制成本/延迟、必要时触发人工接管

### 系统执行流程
```
Goal → State 初始化 → Planner 判断下一步 → Model 生成动作
→ Tools 执行 → State 更新 → Evaluator 检查 → 继续或结束
```

### 动手前五个问题
1. 目标是什么
2. 状态里放什么
3. 哪些能力必须通过工具获得
4. 哪些决策交给模型，哪些交给程序
5. 什么时候结束、失败、或人工介入

## 4. 为什么 Agent Demo 一落地就不稳定

### Demo 的天然偏向
- 乐观输入、短链路、少量工具、单次成功样例
> 只能证明"有可能可行"，不能证明"长期可用"

### 六大断层

| 断层 | 问题 | 对策 |
|------|------|------|
| 目标太模糊 | 不知何时结束、范围膨胀 | 把目标写窄 |
| 状态没设计 | 遗忘已执行步骤、重复调用 | 结构化保存中间结果 |
| 工具调用乐观 | API超时/格式变化/权限失败 | 重试+降级+兜底 |
| "会思考"≠"会执行" | 声称完成但未真正执行 | 检查实际执行了什么 |
| 无结束条件 | 循环不止、成本失控 | 硬性上限+超时退出 |
| 无可观测性 | 只看"失败"无法维护 | 全链路 trace + log |

### 从 Demo 到生产的正确路径
1. 缩窄目标
2. 明确状态结构
3. 为工具调用添加异常处理
4. 定义结束条件和预算上限
5. 增加日志、追踪和人工接管点

> ❌ 错误顺序：换更强模型 → 堆更多 Prompt → 期望自行变稳定

## 5. Tool Calling 入门

### 模型需要工具的原因
模型擅长**理解、推理、生成**；工具负责**与外部世界交互**。

### 关键分工

| 角色 | 职责 |
|------|------|
| **模型** | 说明需要哪个工具、参数是什么 |
| **程序** | 真正执行工具、校验参数、处理异常 |

### 好工具的五个要求
1. **职责清晰** — 一个工具不做多件事
2. **输入清晰** — 结构化字段、可校验
3. **输出清晰** — 返回值稳定
4. **权限清晰** — 读写删执行有边界
5. **错误可处理** — 区分参数/权限/网络/空数据错误

### 最容易踩的坑
- 模型假装调用过工具（编造结果）
- 工具接口设计过于宽泛
- 工具返回结果太脏
- 没有调用预算

> 核心策略：先做"可控工具"，再做"强大工具"

## 6. Memory 设计模式

### 三类核心区分

| 类型 | 说明 | 示例 |
|------|------|------|
| **State（状态）** | 当前任务的结构化执行现场 | 分析进度、已查询数据 |
| **短期记忆** | 当前会话中的上下文 | 前几轮对话、临时约束 |
| **长期记忆** | 跨会话的长期沉淀 | 用户偏好、历史决策 |

### 推荐设计顺序
1. **先设计好 State** — 结构化任务状态
2. **再处理会话内上下文** — 任务连续性
3. **最后考虑长期记忆** — 评估真正需求

> "很多所谓 memory 问题，本质上是 state 没设计好。"

### 四种常见模式

| 模式 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 对话窗口保留 | 保留最近几轮 | 简单 | 长任务撑爆上下文 |
| 摘要式记忆 | 压缩为摘要 | 省窗口 | 可能失真 |
| 结构化状态存储 | 保存在明确字段 | 可调试可恢复 | 设计成本高 |
| 检索式长期记忆 | 存入向量库需时召回 | 不占上下文 | 召回不稳定 |

### Memory vs RAG

| 维度 | RAG | Memory |
|------|-----|--------|
| 核心问题 | 从外部知识取回相关内容 | 记住与当前主体相关的信息 |
| 示例 | 市场研究报告 | 用户偏好 |

## 7. Planning、Reflection、RAG 分别解决什么问题

| 概念 | 解决的问题 | 一句话 |
|------|-----------|--------|
| **Planning** | 下一步该做什么 | 安排动作 |
| **Reflection** | 刚才做得对不对 | 检查质量 |
| **RAG** | 我现在缺什么信息 | 补充信息 |

### 反模式警示
> "不要把'缺信息'误判成'要多思考'"
- 缺外部知识 → 让模型 Planning **无用**
- 缺结果校验 → 补 RAG **无用**
- 缺任务拆解 → 反复 Reflection **无用**

### 渐进建设顺序
1. 先把任务主流程做通
2. 判断是否缺外部信息 → 加 RAG
3. 判断输出是否不稳定 → 加 Reflection
4. 任务复杂度足够高 → 增强 Planning

## 8. 单 Agent 和多 Agent 的边界

### 首要原则
> **大多数项目第一版应优先从单 Agent 做起。**

### 单 Agent 优先的理由
- 成本更低（无跨 Agent 通信开销）
- 状态更集中
- 调试更容易
- 行为更可解释

### 多 Agent 真正有价值的场景
1. 职责确实不同
2. 上下文压力太大（需隔离）
3. 任务可并行
4. 需要对抗或复核机制

### 常见误区
> 多角色 Prompt ≠ 多 Agent

如果只是切换 system prompt 名字，实质是"多角色提示词"，不是真正的多 Agent。

### 务实判断四问
1. 单 Agent 真的做不好，还是觉得多 Agent 更高级？
2. 各角色间是否有明确且稳定的职责边界？
3. 拆分后复杂度增加是否值得？
4. 是否真的需要并行、复核或对抗？

> "如果单 Agent 还没做稳，多 Agent 大概率只会把问题复制并放大。"
